Apache Ozone on Zoned Storage

Apache Ozone is a distributed object store with S3, Hadoop file system (ofs) and native client interfaces. The Ozone Manager (OM) stores the namespace (volumes, buckets and keys). The Storage Container Manager (SCM) allocates blocks and groups them into containers. Datanodes store each container as a directory of block files on local file systems, one per drive.

Place the Datanode data directories on zoned XFS file systems on host-managed SMR disks or NVMe ZNS SSDs. With the default FILE_PER_BLOCK layout, each block (256 MiB by default) is a single file written sequentially. XFS handles zone writes and space reclamation, and Ozone needs no zoned-device support. Keep the OM and SCM databases, the Datanode Ratis logs and the per-volume container RocksDB on conventional SSD storage.

System Requirements
  • Linux kernel: 6.15+ with CONFIG_XFS_FS and CONFIG_XFS_RT enabled
  • xfsprogs: 6.15+
  • Apache Ozone 2.2.2 (tested with the binary release tarball)
  • Java 11 or 17 (tested with Eclipse Temurin 17.0.21)
  • Tested on kernel 6.17.7 with xfsprogs 6.19.0, using zloop emulated zoned devices

How It Fits Together​

A single-node deployment runs the SCM, OM and Datanode daemons and, optionally, the S3 Gateway. The Ozone production deployment guide lists ext4 and XFS as supported local file systems, recommends SSDs for all metadata and Ratis logs, and recommends JBOD (no RAID or LVM) for data drives.

DataSettingPlacement

SCM database (containers, pipelines)ozone.scm.db.dirsconventional SSD
Datanode ID, OM/SCM Ratis logs, fallback metadataozone.scm.datanode.id.dir, ozone.metadata.dirsconventional SSD
Datanode Ratis (write pipeline) logshdds.container.ratis.datanode.storage.dirconventional SSD

Quick Start​

These steps configure a single-node Ozone cluster with container data on a zoned drive. Run commands prefixed with # as root and commands prefixed with $ as the ozone account created in Step 1, in a login shell (sudo -iu ozone). The release is downloaded and extracted in its home directory.

Step 1: Prepare a Zoned XFS File System​

Check the XFS requirements before formatting the drive.

For an SMR hard disk (or any zoned device with conventional zones at the start of its address space), format the whole disk and mount it:

# mkfs.xfs /dev/sda
meta-data=/dev/sda               isize=512    agcount=4, agsize=65536 blks
...
realtime =internal               extsz=4096   blocks=3932160, rtextents=3932160
         =                       rgcount=60   rgsize=65536 extents
         =                       zoned=1      start=262144 reserved=0
Resetting zones...Done.
# mkdir -p /data/disk1
# mount -o noatime /dev/sda /data/disk1

The zoned=1 field identifies a zoned realtime device. The kernel log confirms the zoned mount:

XFS (sda): EXPERIMENTAL zoned RT device feature enabled.  Use at your own risk!
XFS (sda): Mounting V5 Filesystem e23f343d-bd35-4bf0-a7f6-50c9a9dcfb83
XFS (sda): Ending clean mount
XFS (sda): 60 zones of 65536 blocks size (15 max open)

An NVMe ZNS SSD has no conventional zones and requires a separate conventional block device for XFS metadata, such as a conventional namespace or a small SSD partition. Specify the zoned namespace as the realtime device:

# mkfs.xfs -r rtdev=/dev/nvme0n2 /dev/nvme1n1
...
realtime =/dev/nvme0n2           extsz=4096   blocks=4194304, rtextents=4194304
         =                       rgcount=64   rgsize=65536 extents
         =                       zoned=1      start=0 reserved=0
Discarding blocks...Done.
Resetting zones...Done.
# mkdir -p /data/disk2
# mount -o noatime,rtdev=/dev/nvme0n2 /dev/nvme1n1 /data/disk2

The ZNS layout was tested with a zloop device without conventional zones as the realtime device and a 1 GiB loop device as the metadata device, not with ZNS hardware. See the XFS page for details on both cases.

tip

To try this setup without a zoned drive, create an emulated device with zloop as described in Zoned Block Device Emulation and use it in place of /dev/sda. This guide was tested with 16 GiB zloop devices with 256 MiB zones (4 conventional zones for the SMR case, none for the ZNS case).

To mount the file systems at boot, add them to /etc/fstab. Prefer persistent /dev/disk/by-id/ names to /dev/sdX and /dev/nvmeXnY names. These entries were not tested on the test host.

# SMR HDD
/dev/sda      /data/disk1  xfs  defaults,noatime                    0 0
# NVMe ZNS SSD with a conventional metadata device
/dev/nvme1n1  /data/disk2  xfs  defaults,noatime,rtdev=/dev/nvme0n2  0 0

Create the non-root account that runs Ozone, with a home directory for the release tarball:

# useradd --create-home --user-group --shell /bin/bash ozone

Create the Datanode directory on the zoned file system and the metadata directories on conventional SSD storage (/var/lib/ozone in this example), owned by the ozone account:

# mkdir -p /data/disk1/ozone
# mkdir -p /var/lib/ozone/{metadata,om,scm,dn-id,dn-ratis,container-db}
# chown -R ozone:ozone /data/disk1/ozone /var/lib/ozone

New directories inherit the rtinherit attribute (t) from the file system root, so container files created under /data/disk1/ozone are stored on the zoned device:

$ xfs_io -c lsattr /data/disk1/ozone
-------t--------X /data/disk1/ozone

Step 3: Configure Ozone​

Edit etc/hadoop/ozone-site.xml. Set every metadata location to conventional storage and hdds.datanode.dir to the zoned file system. A single Datanode requires replication factor ONE and an SCM safe-mode threshold of one Datanode.

    <name>ozone.scm.names</name>
    <value>localhost</value>
  </property>
  <property>
    <name>ozone.om.address</name>
    <value>localhost</value>
  </property>
  <property>
    <name>ozone.metadata.dirs</name>
    <value>/var/lib/ozone/metadata</value>
  </property>
  <property>
    <name>ozone.om.db.dirs</name>
    <value>/var/lib/ozone/om</value>
  </property>
  <property>
    <name>ozone.scm.db.dirs</name>
    <value>/var/lib/ozone/scm</value>
  </property>
  <property>
    <name>ozone.scm.datanode.id.dir</name>
    <value>/var/lib/ozone/dn-id</value>
  </property>
  <property>
    <name>hdds.container.ratis.datanode.storage.dir</name>
    <value>/var/lib/ozone/dn-ratis</value>
  </property>
  <property>
    <name>hdds.datanode.container.db.dir</name>
    <value>/var/lib/ozone/container-db</value>
  </property>
  <property>
    <name>hdds.datanode.dir</name>
    <value>/data/disk1/ozone</value>
  </property>
  <property>
    <name>ozone.server.default.replication</name>
    <value>1</value>
  </property>
  <property>
    <name>hdds.scm.safemode.min.datanode</name>

  </property>

note

The Datanode reports a minimum free space per volume to SCM (the larger of hdds.datanode.volume.min.free.space, 20 GB by default, and hdds.datanode.volume.min.free.space.percent, 2% by default). SCM creates a write pipeline only if a volume has room for a full container (ozone.scm.container.size, 5 GB by default) on top of this reserve, so drives with less than about 25 GB available get no pipeline. The tests used 16 GiB emulated drives and set hdds.datanode.volume.min.free.space to 512MB. Production-size SMR and ZNS drives do not need this change. See Troubleshooting.

Production Notes​

Multiple Zoned Drives per Datanode​

Format and mount each zoned drive as a separate XFS file system and list one directory per drive in hdds.datanode.dir, separated by commas. Do not combine zoned drives with LVM or RAID; Ozone replicates or erasure-codes data across Datanodes.

  <property>
    <name>hdds.datanode.dir</name>
    <value>/data/disk1/ozone,/data/disk2/ozone,/data/disk3/ozone</value>
  </property>

The Datanode creates one container RocksDB per volume under hdds.datanode.container.db.dir. In a test with an SMR-style and a ZNS-style volume, the Datanode placed new containers on both volumes, and block files on both had the realtime attribute. hdds.datanode.dir entries can be tagged with a storage type such as [DISK] for storage policies.

Container RocksDB Placement​

Without hdds.datanode.container.db.dir, the container RocksDB (container.db) is created inside each data volume, and its files are stored on the zoned device (realtime attribute r). The test cluster ran in this configuration without errors. RocksDB writes its write-ahead log, MANIFEST and SST files as new files, which fits zoned XFS, but block metadata updates then share the zoned drive with block data. On an SMR disk, this adds small writes and reads that compete with block I/O. Set hdds.datanode.container.db.dir to an SSD directory, as recommended by the Ozone documentation. Back up the SSD: losing a volume's container database makes the containers on that volume unusable.

Preallocation, Direct I/O and Other Zoned XFS Limitations​

The Datanode was traced with strace during the tests:

  • Block files are opened with O_RDWR|O_CREAT and written with buffered I/O. No fallocate call was issued on block files.
  • RocksDB calls fallocate(FALLOC_FL_KEEP_SIZE) on new WAL and MANIFEST files (allow_fallocate defaults to true). On zoned XFS this returns EOPNOTSUPP, and RocksDB continues without preallocation. This only affects a container database stored on the zoned file system.
  • No file on the data volume was opened with O_DIRECT.

Ozone does not use reflinks or disk quotas on the data volumes, so the zoned XFS limitations did not affect the tested operations. The Datanode Ratis log directory was on SSD in all tests; Ratis logs on zoned XFS were not tested.

Replication on a Single Node​

With one Datanode, use replication factor ONE (ozone.server.default.replication = 1, or --type=RATIS --replication=ONE per key). A key written with RATIS/THREE fails because SCM cannot create a three-node pipeline:

$ bin/ozone sh key put --type=RATIS --replication=THREE /vol1/bucket1/three.bin small.bin
INTERNAL_ERROR Unable to allocate a container to the block of size: 268435456, replicationConfig: RATIS/THREE. Cannot create pipeline as it would exceed the limit per datanode: 2 replicationConfig: RATIS/THREE

Use three or more Datanodes for RATIS/THREE, and at least the number of data plus parity units for erasure coding (for example 5 for RS-3-2). Multi-node deployments were not tested.

Container Close, Deletes and Space Reclaim​

  • Containers are closed when they reach hdds.container.close.threshold (90%) of ozone.scm.container.size (5 GB by default), or on request with ozone admin container close. In the test, a manual close took about three minutes from CLOSING to CLOSED. Closing does not rewrite block files.

  • ozone sh key delete removes the key from the OM immediately. Datanodes delete the block files later: the OM key-deleting service, the SCM block-deleting service and the Datanode block-deleting service each run about once per minute (ozone.block.deleting.service.interval, hdds.scm.block.deleting.service.interval, hdds.datanode.block.deleting.service.interval). In the tests, block files were removed and file system usage dropped 1.5 to 2.5 minutes after the delete:

    16:47:32  delete 8 keys (8 GiB)        used: 8961 MiB  9473 MiB  blocks=72
    16:49:35                               used: 8961 MiB  9473 MiB  blocks=72
    16:49:55                               used: 6401 MiB  3841 MiB  blocks=40

  • XFS resets zones that no longer contain valid data. After the deletes above, 38 of the 64 zones of the ZNS-style drive were empty again. Partially valid zones are reclaimed by XFS garbage collection when free space runs low. A 256 MiB block file can be spread over several zones (blocks written concurrently share open zones), as in the xfs_bmap output above.

XFS Tuning​

By default, XFS uses all but one of the drive's open zones for file writes. Concurrent block writes on a Datanode share this limit. Use the max_open_zones mount option to lower it, or raise zonegc_low_space to start garbage collection earlier for workloads with many deletes. Read the current values from sysfs:

# cat /sys/fs/xfs/sda/zoned/max_open_zones
14
# cat /sys/fs/xfs/sda/zoned/zonegc_low_space
0
# echo 5 > /sys/fs/xfs/sda/zoned/zonegc_low_space

See the XFS tuning section for details.

Troubleshooting​

No Write Pipeline on Small Drives​

ozone admin pipeline list shows no pipelines, and the Datanode log contains:

WARN volume.HddsVolume: Volume /data/disk1/ozone/hdds has insufficient space for write operation. Available: 15030882297, Free space to spare: 21474836480

The volume is smaller than the default minimum free space of 20 GB (hdds.datanode.volume.min.free.space). This is unrelated to zoned storage and occurs with small or emulated drives. Lower the setting (for example 512MB for test drives), restart the Datanode and wait for SCM to create the pipeline.

Writes Fail While the Drives Still Have Free Space​

Clients report:

INTERNAL_ERROR org.apache.hadoop.ozone.om.exceptions.OMException: Unable to allocate a container to the block of size: 268435456, replicationConfig: RATIS/ONE. null

and the Datanode log shows:

INFO volume.CapacityVolumeChoosingPolicy: No volumes have enough space for a new container.  Most available space: 4830223499 bytes; required space: 5368709120, ...
WARN keyvalue.KeyValueHandler: Operation: CreateContainer , ... Message: Container creation failed, due to disk out of space , Result: DISK_OUT_OF_SPACE ...

A new container requires free space for a full container (ozone.scm.container.size, 5 GB by default) on one volume. In the test, writes stopped with 37% of the 2 × 16 GiB test drives free. The failure also closed the write pipeline and its open containers; SCM created a new pipeline and all previously written keys remained readable with matching checksums. Deleting keys freed space (see above), and new writes succeeded afterwards. This is independent of zoned storage. On small drives, lower ozone.scm.container.size (the first test used 1GB).

Block Files Are Not on the Zoned Device​

If xfs_io -c lsattr does not show the r flag on .block files, the rtinherit attribute was cleared on a parent directory, or hdds.datanode.dir points to a directory on another file system. Check the mount with df and the directory attributes with xfs_io -c lsattr; see Placing Data on the Main Device.
