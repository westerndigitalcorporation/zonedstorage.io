CubeFS on Zoned Storage

CubeFS is a distributed file system with a POSIX interface (FUSE client) and an S3-compatible interface (ObjectNode). A Master manages the cluster, MetaNodes keep the file system metadata in memory and on local disk, and DataNodes store file contents. Each DataNode data partition is a directory of extent files on a local disk: files larger than 1 MiB use normal extents (one file of up to 128 MiB per extent). Smaller files are appended to 64 shared tiny extent files and deleted by punching holes into them.

Place the DataNode disk directories on zoned XFS file systems on host-managed SMR disks or NVMe ZNS SSDs, one file system per drive. XFS writes extent data sequentially into the zones, frees punched ranges and deleted files, and reclaims zones. The Master and MetaNode data stay on conventional storage. The DataNode needs no zoned-device support. The blobstore erasure-coding subsystem does not work on zoned XFS (see Blobstore Is Not Supported).

System Requirements
  • Linux kernel: 6.15+ with CONFIG_XFS_FS and CONFIG_XFS_RT enabled
  • xfsprogs: 6.15+
  • FUSE support (/dev/fuse) on client hosts
  • CubeFS 3.6.0 (tested with the cubefs-3.6.0-linux-amd64.tar.gz release binaries, commit f6a14a59, on Linux 6.17.7 with xfsprogs 6.19.0)

How It Fits Together​

A single-node replica deployment runs four server roles from the same cfs-server binary, plus the cfs-client FUSE client:

ComponentStoresPlacement
MasterCluster topology, volumes, users (walDir, storeDir)Conventional SSD
MetaNodeInodes and dentries (metadataDir, raftDir)Conventional SSD
DataNodeData partitions with extent files (disks)Zoned XFS, one per drive
DataNode raft logRaft WAL of the node (raftDir)Conventional SSD
ObjectNodeNo persistent data; serves S3 from the volumes-
cfs-clientNo persistent data; FUSE mount of a volume-

Each data partition directory on a zoned drive contains:

  • Extent files 1 to 64 (tiny extents, shared by small files) and 1025, 1026, ... (normal extents, up to 128 MiB each).
  • Small metadata files: EXTENT_CRC (per-block checksums), META, APPLY, EXTENT_META, NORMALEXTENT_DELETE, TINYEXTENT_DELETE and a per-partition raft WAL in wal_N/.

All of these files inherit the realtime attribute and are stored in sequential zones. XFS keeps its own metadata (inodes, directories) in the conventional zones of an SMR disk, or on a separate conventional device for NVMe ZNS.

          conventional SSD                       zoned drives (XFS)
     +-------------------------+      +--------------------+  +--------------------+
     | /var/lib/cubefs/master  |      | /data/disk1/cubefs |  | /data/disk2/cubefs |
     | /var/lib/cubefs/metanode|      |  datapartition_1_  |  |  datapartition_7_  |
     | /var/lib/cubefs/datanode|      |  datapartition_2_  |  |  ...               |
     +-------------------------+      +--------------------+  +--------------------+
      Master, MetaNode, raft logs          DataNode "disks" (one entry per drive)

Quick Start​

These steps set up a single-node cluster with one replica, two zoned data drives, a FUSE mount and the S3 endpoint. CubeFS recommends at least three nodes with three replicas for production. Run all commands as root.

Step 1: Prepare Zoned XFS File Systems​

Check the XFS requirements before formatting the drives.

For an SMR disk with conventional zones, format the whole disk:

# mkfs.xfs -L CUBEFSDISK1 /dev/sda
meta-data=/dev/sda               isize=512    agcount=4, agsize=65536 blks
         =                       sectsz=4096  attr=2, projid32bit=1
         =                       crc=1        finobt=1, sparse=1, rmapbt=1
         =                       reflink=0    bigtime=1 inobtcount=1 nrext64=1
         =                       exchange=1   metadir=1
data     =                       bsize=4096   blocks=262144, imaxpct=25
         =                       sunit=0      swidth=0 blks
naming   =version 2              bsize=4096   ascii-ci=0, ftype=1, parent=1
log      =internal log           bsize=4096   blocks=25087, version=2
         =                       sectsz=4096  sunit=1 blks, lazy-count=1
realtime =internal               extsz=4096   blocks=3932160, rtextents=3932160
         =                       rgcount=60   rgsize=65536 extents
         =                       zoned=1      start=262144 reserved=0
Resetting zones...Done.
# mkfs.xfs -L CUBEFSDISK2 /dev/sdb
# mkdir -p /data/disk1 /data/disk2
# mount -o noatime LABEL=CUBEFSDISK1 /data/disk1
# mount -o noatime LABEL=CUBEFSDISK2 /data/disk2

The zoned=1 field identifies a zoned realtime device. The kernel log shows the number of zones and the open-zone limit:

XFS (sda): EXPERIMENTAL zoned RT device feature enabled.  Use at your own risk!
XFS (sda): Mounting V5 Filesystem 157cbf6f-bd13-4ded-a090-2116dfbd7096
XFS (sda): Ending clean mount
XFS (sda): 60 zones of 65536 blocks size (15 max open)

An NVMe ZNS namespace has no conventional zones. Put the XFS metadata on a conventional block device, such as a conventional namespace or an SSD partition, and use the ZNS namespace as the realtime device:

# mkfs.xfs -L CUBEFSDISK1 -r rtdev=/dev/nvme0n2 /dev/nvme1n1
# mount -o noatime,rtdev=/dev/nvme0n2 LABEL=CUBEFSDISK1 /data/disk1

The ZNS commands were not tested for this guide. See XFS for details on both cases.

tip

For emulated hardware, create zloop devices as described in Zoned Block Device Emulation and use them in place of /dev/sda and /dev/sdb. This guide was tested with two 16 GiB zloop devices with 256 MiB zones and four conventional zones.

Add the file systems to /etc/fstab to mount them at boot (not tested in this setup):

# SMR HDDs
LABEL=CUBEFSDISK1  /data/disk1  xfs  defaults,noatime  0  0
LABEL=CUBEFSDISK2  /data/disk2  xfs  defaults,noatime  0  0
# NVMe ZNS SSD with a conventional metadata device
LABEL=CUBEFSDISK1  /data/disk1  xfs  defaults,noatime,rtdev=/dev/nvme0n2  0  0

Create the DataNode directories on the zoned file systems. They inherit the rtinherit attribute (t) from the file system root, so all files created below them are placed on the zoned device:

# mkdir /data/disk1/cubefs /data/disk2/cubefs
# xfs_io -c lsattr /data/disk1/cubefs
-------t--------X /data/disk1/cubefs

Production Notes​

Disks, Reserved Space and Capacity​

  • One file system per drive. Format each SMR disk or ZNS namespace as a separate zoned XFS file system and list one directory per drive in the DataNode disks setting. Do not combine zoned drives with LVM or RAID; CubeFS replicates data partitions across DataNodes.
  • Read-only threshold. The DataNode raises diskRdonlySpace to at least 5 GiB. It subtracts this value from each disk's capacity and stops creating new extents on the disk when its free space falls below it. On the 16 GiB test drives (14 GiB of sequential zones), 9 GiB per drive was usable. On large SMR disks, this is negligible.
  • Media type. Set mediaType in datanode.json to 2 for SMR disks and 1 for SSDs. The volume must be created in the matching storage pool (see Troubleshooting).
  • Conventional storage for metadata. Keep the Master (walDir, storeDir), MetaNode (metadataDir, raftDir) and DataNode raftDir on SSDs or other conventional storage.

Punch Hole, Preallocation and Overwrites​

The DataNode uses fallocate() in three ways. On zoned XFS:

  • Punch hole (FALLOC_FL_PUNCH_HOLE | FALLOC_FL_KEEP_SIZE) works. The DataNode uses it to delete small files from tiny extents and to clear entries in EXTENT_CRC. In the test, the deleted ranges were freed (the tiny extent file had no allocated blocks afterwards); XFS garbage collection reclaims the space in partially valid zones.
  • Preallocation (FALLOC_FL_KEEP_SIZE) of the EXTENT_CRC files fails with EOPNOTSUPP, because zoned XFS does not support persistent preallocation. The DataNode ignores this error and writes the checksums without preallocation. Tracing the DataNode showed 150 failed preallocation calls and no errors in its logs during the tests.
  • Overwrites of existing file data (random writes through FUSE) work. In the test, four 16 MiB overwrites into a 300 MiB file produced the expected checksum. XFS writes overwritten data out of place.

The DataNode does not use reflink or quotas.

Deletes and Space Reclaim​

CubeFS deletes file data asynchronously. In the test, deleting 1 GiB of large files reduced the drive usage reported by df within about 30 to 60 seconds: the DataNode removed the normal extent files, and XFS reset the zones that no longer held valid data. Repeated cycles of writing 4 GiB and deleting 2 GiB, run after the volume had been filled once, completed without errors. All 14 remaining 1 GiB files, the overwritten file and the S3 object passed checksum verification afterwards.

Small files in tiny extents leave invalid ranges in partially used zones after deletion. For workloads with many small-file deletes, consider raising zonegc_low_space so that XFS starts garbage collection earlier:

# cat /sys/fs/xfs/sda/zoned/max_open_zones
14
# cat /sys/fs/xfs/sda/zoned/zonegc_low_space
0
# echo 5 > /sys/fs/xfs/sda/zoned/zonegc_low_space

Open Zones​

XFS uses one fewer than the device's open-zone limit for file data (14 on the test drives). Each data partition appends to its own extent files, and XFS tries to keep concurrently written files in separate zones, so many active data partitions per disk share this limit. Use the max_open_zones mount option to lower it for SMR disks. See XFS tuning.

Restart​

After stopping and restarting the DataNode, it reloaded its data partitions from the zoned drives, and all files read back with the same checksums.

Blobstore Is Not Supported​

The blobstore erasure-coding subsystem stores data in chunk files on the BlobNode disks. When it creates a chunk, the BlobNode preallocates the 4 KiB chunk header with fallocate() mode 0 (blobnode/core/storage/datafile.go, writeMeta()) and fails if that call fails. On zoned XFS, the call returns EOPNOTSUPP:

PreAllocate(0, 4096): operation not supported
PunchHole(0, 4096): <nil>

This output is from a test program calling the BlobNode's sys.PreAllocate() and sys.PunchHole() functions on a zoned XFS file system. The same calls succeed on regular XFS. Use replica volumes with DataNodes on zoned drives, and keep blobstore disks on conventional storage.

Troubleshooting​

"poolId(1) not found in available pools(2)"​

# cfs-cli volume create zvol cubefs --capacity 20 --replica-num 1 -y
Error: Create volume failed case:
poolId(1) not found in available pools(2) for zoneName(default)

The default storage pool (1) is for SSD media. In a cluster where all DataNodes have mediaType 2 (HDD), create the volume with --poolId 2 --pools 2.

Small Files Are Not Written to Tiny Extents Right After Startup​

For about one minute after a data partition is created or the DataNode starts, its tiny extents are not yet available. Writes of small files are retried in normal extents, and the DataNode warning log shows:

[WARN ] repl_protocol.go:434: ... ResultMesg(DiskNoSpaceErr)] ... err[ActionPreparePkt_checkPacketAndPrepare partition 3 GetAvailableTinyExtent error no available extent]

The data is written correctly. The tiny extents become available after the first tiny extent repair cycle. This behavior is not specific to zoned storage.

Writes Fail with "no space left on the device" While XFS Has Free Space​

The client reports an I/O error, and the DataNode error log shows:

[ERROR] repl_protocol.go:436: ... _Opcode(OpCreateExtent)_CRC(0)_ResultMesg(DiskNoSpaceErr)] ... err[ActionCreateExtent:_no space left on the device]

The disk reached the diskRdonlySpace threshold (at least 5 GiB per disk), and its data partitions became read-only. In the test, this happened when df still reported about 4.9 GiB free per drive. Delete data or add drives. After deletion, the data partitions became writable again within about a minute.

Extent Files Are Not on the Zoned Device​

If xfs_io -c lsattr does not show the r flag on extent files, the disks entry is not on the zoned file system, or the rtinherit attribute was cleared on a parent directory. Check the mount with df and the directory attributes with xfs_io -c lsattr; see Placing Data on the Main Device.
