NVIDIA AIStore on Zoned Storage

NVIDIA AIStore (AIS) is a scale-out object storage system. A cluster consists of proxies (gateways), which serve the API and own the cluster map, and targets, which store objects. Each target stores objects as regular files, with per-object metadata in extended attributes, on a set of mountpaths. A mountpath is a directory on a local file system. AIS requires each mountpath to be a separate file system, and recommends XFS.

Format each host-managed SMR disk or NVMe ZNS namespace with zoned XFS and configure each file system as one target mountpath. Object contents go to the sequential zones. XFS metadata, including the extended attributes that hold AIS object metadata, goes to the disk's conventional zones (SMR) or a separate conventional device (ZNS). The proxy and the target's own configuration directory stay on conventional storage. AIS uses standard file I/O and needs no zoned-device support.

System Requirements
  • Linux kernel: 6.15+ with CONFIG_XFS_FS and CONFIG_XFS_RT enabled
  • xfsprogs: 6.15+
  • AIStore 5.2 (release tag v1.5.2): aisnode built from source with Go 1.27.3, ais CLI 1.34
  • Tested on Linux 6.17.7 with xfsprogs 6.19.0, with one proxy and one target with four mountpaths on 16 GiB zloop devices

How It Fits Together​

ComponentStoresPlacement
Proxy (aisnode -role=proxy)Cluster map, bucket metadata, cluster configuration in its confdirConventional storage (SSD)
Target (aisnode -role=target)Configuration and copies of cluster metadata in its confdirConventional storage (SSD)
Target mountpathsObjects under <mountpath>/@ais/<bucket>/%ob/, work files under %wk/, small metadata files (.ais.vmd, .ais.bmd, .ais.smap) at the mountpath rootOne zoned XFS file system per drive
Object metadata (user.ais.lom xattr)Checksum, version, size, copy locationsXFS metadata: conventional zones or ZNS metadata device
              conventional SSD                       zoned drives (XFS)
       +----------------------------+   +-------------+       +-------------+
proxy  | /var/lib/ais/proxy         |   | /data/disk1 |  ...  | /data/disk4 |
       +----------------------------+   |  @ais/...   |       |  @ais/...   |
       +----------------------------+   +-------------+       +-------------+
target | /var/lib/ais/target        |         target mountpaths (fspaths)
       +----------------------------+

A target distributes objects across its mountpaths by object name. With mirroring enabled on a bucket, a target keeps additional copies of each object on other mountpaths. Erasure coding distributes slices across targets, not mountpaths.

Quick Start​

These steps set up one proxy and one target with four zoned drives on one host. Commands prefixed with # run as root. Commands prefixed with $ run as the ais account created in Step 1, in a login shell (sudo -iu ais), which builds AIS in its home directory and owns the mountpaths.

Step 1: Prepare Zoned XFS File Systems​

Check the XFS requirements before formatting the drives.

For SMR disks (or any zoned device with conventional zones at the start of its address space), format each whole disk with a label:

# mkfs.xfs -L AISDISK1 /dev/sda
meta-data=/dev/sda               isize=512    agcount=4, agsize=65536 blks
         =                       sectsz=4096  attr=2, projid32bit=1
         =                       crc=1        finobt=1, sparse=1, rmapbt=1
         =                       reflink=0    bigtime=1 inobtcount=1 nrext64=1
         =                       exchange=1   metadir=1
data     =                       bsize=4096   blocks=262144, imaxpct=25
         =                       sunit=0      swidth=0 blks
naming   =version 2              bsize=4096   ascii-ci=0, ftype=1, parent=1
log      =internal log           bsize=4096   blocks=25087, version=2
         =                       sectsz=4096  sunit=1 blks, lazy-count=1
realtime =internal               extsz=4096   blocks=3932160, rtextents=3932160
         =                       rgcount=60   rgsize=65536 extents
         =                       zoned=1      start=262144 reserved=0
Resetting zones...Done.
# mkfs.xfs -L AISDISK2 /dev/sdb
# mkfs.xfs -L AISDISK3 /dev/sdc
# mkfs.xfs -L AISDISK4 /dev/sdd

zoned=1 in the realtime section confirms the zoned realtime device. Create the account that builds and runs AIS. The build in Step 2 needs a home directory and Go in its PATH:

# useradd --create-home --user-group --shell /bin/bash ais

Mount the file systems with noatime, which the AIS performance guide recommends, and give the ais account ownership:

# mkdir -p /data/disk{1..4}
# for i in 1 2 3 4; do mount -o noatime LABEL=AISDISK$i /data/disk$i; done
# chown ais:ais /data/disk{1..4}
# findmnt -t xfs -o SOURCE,TARGET,OPTIONS
SOURCE   TARGET      OPTIONS
/dev/sda /data/disk1 rw,noatime,attr2,inode64,logbufs=8,logbsize=32k,noquota,max_open_zones=15
/dev/sdb /data/disk2 rw,noatime,attr2,inode64,logbufs=8,logbsize=32k,noquota,max_open_zones=15
/dev/sdc /data/disk3 rw,noatime,attr2,inode64,logbufs=8,logbsize=32k,noquota,max_open_zones=15
/dev/sdd /data/disk4 rw,noatime,attr2,inode64,logbufs=8,logbsize=32k,noquota,max_open_zones=15

The kernel log reports the zone count and open-zone limit for each file system:

XFS (sda): EXPERIMENTAL zoned RT device feature enabled.  Use at your own risk!
XFS (sda): Mounting V5 Filesystem a0b461b9-937d-4da9-84fa-bee945f1c97e
XFS (sda): Ending clean mount
XFS (sda): 60 zones of 65536 blocks size (15 max open)

An NVMe ZNS namespace has no conventional zones. Place the XFS metadata on a conventional block device, such as a conventional namespace or an SSD partition, and specify the ZNS namespace as the realtime device:

# mkfs.xfs -L AISDISK1 -r rtdev=/dev/nvme0n2 /dev/nvme1n1
# mount -o noatime,rtdev=/dev/nvme0n2 LABEL=AISDISK1 /data/disk1

The ZNS commands were not tested for this guide. See XFS for details on both cases.

tip

To try this setup without zoned drives, create emulated devices with zloop as described in Zoned Block Device Emulation and use them in place of /dev/sda to /dev/sdd. This guide was tested with four 16 GiB zloop devices with 256 MiB zones and four conventional zones each.

To mount the file systems at boot, add one /etc/fstab entry per drive (not tested on the test host):

# SMR HDDs
LABEL=AISDISK1  /data/disk1  xfs  defaults,noatime  0  2
LABEL=AISDISK2  /data/disk2  xfs  defaults,noatime  0  2
LABEL=AISDISK3  /data/disk3  xfs  defaults,noatime  0  2
LABEL=AISDISK4  /data/disk4  xfs  defaults,noatime  0  2
# NVMe ZNS SSD with a conventional metadata device
LABEL=AISDISK1  /data/disk1  xfs  defaults,noatime,rtdev=/dev/nvme0n2  0  2

NVMe device names can change across reboots. Prefer a /dev/disk/by-id/nvme-... name for the rtdev= option.

Step 2: Build AIStore​

The v1.5.2 release assets contain the ais CLI (ais-linux-amd64.tar.gz) but not the aisnode server binary. Build both from the release tag. The go.mod file requires Go 1.27; if your installed Go is older, select a toolchain explicitly:

$ git clone --depth 1 -b v1.5.2 https://github.com/NVIDIA/aistore.git
$ cd aistore
$ GOTOOLCHAIN=go1.27.3 make node cli

...

*** 'source cmd/cli/autocomplete/bash' or 'source cmd/cli/autocomplete/zsh'

# install -m 755 ~ais/go/bin/aisnode ~ais/go/bin/ais /usr/local/bin/

Step 7: Mirror Objects Across Mountpaths​

A bucket with mirroring enabled keeps the configured number of copies of each object on different mountpaths of the same target. Enabling it starts a job that copies the existing objects:

$ ais bucket props set ais://zbucket mirror.enabled=true mirror.copies=2
"mirror.enabled" set to: "true" (was: "false")

Bucket props successfully updated.
Started job n41CQ4qF1vX. To monitor the progress, run 'ais show job n41CQ4qF1vX'
$ ais object show ais://zbucket/obj.bin --props copies,location
PROPERTY         VALUE
copies           2 [/data/disk4 /data/disk1]
location         t[uZyfRdPY]:mp[/data/disk1, sda, ssd]
$ xfs_io -c lsattr /data/disk4/@ais/zbucket/%ob/obj.bin
r---------------X /data/disk4/@ais/zbucket/%ob/obj.bin

Erasure coding places slices on different targets and needs more than one target. With a single target, the request fails:

$ ais bucket props set ais://zbucket ec.enabled=true ec.data_slices=2 ec.parity_slices=1
Error: ErrNotEnoughTargets: not enough target nodes: EC configuration (D = 2, P = 1) requires at least 4 targets (have 1).

Erasure coding was not tested on zoned XFS for this guide.

AIStore Disk Checks on Zoned XFS​

The tested target accepted zoned XFS mountpaths without changes:

  • File system type and ID. At startup and on mountpath attach, AIS records the device, file system type and file system ID (statfs f_fsid) of each mountpath and refuses two mountpaths on the same file system. Each zoned XFS file system reports its own ID:

    $ ais storage mountpath show --json
    ...
                  "/data/disk1": {
                        "mountpath_label": "",
                        "fs": {
                            "Fs": "/dev/sda",
                            "FsType": "xfs",
                            "FsID": "66339,0"
                        },
                        "disks": [
                            "sda"
                        ],
    ...

    Attaching a bind mount of an already-used file system was rejected:

    $ ais storage mountpath attach uZyfRdPY=/data/disk1x
    Error: FsID 66340,0: filesystem sharing is not allowed: mp[/data/disk1x, fs=/dev/sdb/xfs, unknown] vs "/data/disk2"

  • Extended attributes. The target probes the maximum xattr size on startup. Zoned XFS reported 64 KiB (max xattr size [ 65536 ...] in the log above).

  • Direct I/O. The filesystem health checker (FSHC) reads existing files and writes temporary files in <mountpath>/.$deleted/fshc-on-err/ with O_DIRECT, followed by fsync. Run it on demand per mountpath:

    $ ais storage mountpath fshc uZyfRdPY=/data/disk1
    t[uZyfRdPY]: started filesystem health check on mountpath "/data/disk1"

    The target log shows the result:

    I 16:09:22.139013 fshc:301 3. write 4 temp files to /data/disk1/.$deleted/fshc-on-err
    I 16:09:22.187521 fshc:329 4. remove /data/disk1/.$deleted/fshc-on-err
    I 16:09:22.187559 fshc:185 mp[/data/disk1, sda, ssd] appears to be healthy

    All four mountpaths passed. Tracing the target with strace confirmed openat(..., O_RDWR|O_CREAT|O_TRUNC|O_DIRECT|O_CLOEXEC) calls for the health-check files.

  • No preallocation or reflink. AIS does not call fallocate() or use reflink copies; no fallocate calls were seen while tracing uploads and health checks. Uploads write a work file under %wk/ with buffered I/O. The zoned XFS limitations on preallocation, reflink and quotas do not affect it.

Production Notes​

  • One file system per drive. Format each SMR disk or ZNS namespace as a separate zoned XFS file system and list each as a mountpath. Do not combine zoned drives with LVM or RAID. Use mirroring within a target, or erasure coding or mirroring across targets, for redundancy.

  • Metadata on conventional storage. Keep the proxy and target confdir directories on an SSD. The target also writes small copies of the cluster map and bucket metadata (.ais.smap, .ais.bmd, .ais.vmd) to each mountpath root; these files land on the zoned device, and their XFS metadata and the object xattrs stay on the conventional part of the file system.

  • Uneven fill across mountpaths. AIS selects the mountpath by object name. In a test with about 700 objects of 64 MiB, one mountpath reached 93% usage while the others were at 78% to 80%. Usage close to full increases the work XFS garbage collection has to do on that drive. The AIS capacity watermarks (space.cleanupwm, lowwm, highwm, out_of_space, 65/75/90/95% by default) apply to the target as a whole: above highwm, the target logs _not_ running store cleanup: ... high-wm warnings.

  • Space reclaim after deletes. Deleted objects are removed from the file system immediately. In the test, df usage dropped within seconds after ais object rm and ais rmo --prefix. Deleting large objects left whole zones without valid data, and XFS reset them; an XFS trace of a refill after deleting about 20 GiB showed 16 to 20 zone resets per drive and no garbage-collection victim selection. Workloads that delete small objects mixed with long-lived ones leave partially valid zones that XFS garbage collection must copy. Raising zonegc_low_space starts garbage collection earlier:

    # echo 5 > /sys/fs/xfs/sda/zoned/zonegc_low_space

  • Open zones. By default, XFS writes to at most the device's open-zone limit minus one (14 for the test devices, see /sys/fs/xfs/sda/zoned/max_open_zones). Concurrent uploads to one mountpath share this limit. For SMR disks, a lower max_open_zones mount option can improve throughput. See XFS tuning. The other XFS mount options from the AIS performance guide (largeio, swalloc, allocsize) were not tested on zoned XFS.

  • Restarts. After a cluster shutdown (ais cluster shutdown), unmount and remount, the target found its mountpaths and all objects. A downloaded object matched its original SHA-256 checksum.

  • Tested load. Repeated overwrites of 40 objects of 64 MiB, a fill to 85% with interleaved objects, deletion of half of them and a refill to 93% completed without errors. All 695 remaining objects matched their SHA-256 checksums.

Troubleshooting​

  • "go: download go1.27 for linux/amd64: toolchain not available". GOTOOLCHAIN=auto tries to download the version in go.mod (go 1.27) without a patch level. Name a released toolchain, such as GOTOOLCHAIN=go1.27.3.

  • "http error code 'Service Unavailable'" right after startup. The cluster is still starting (ais show cluster shows the cluster-not-started-yet alert). Wait a few seconds and retry.

  • "filesystem sharing is not allowed". Two mountpaths are on the same file system. Use one zoned XFS file system per mountpath.

  • ais put with several files asks "[Y/N]" and cancels. Multi-file uploads ask for confirmation. Add --yes in scripts.

  • Object files not on the zoned device. If xfs_io -c lsattr does not show the r flag for files under %ob/, check that mkfs.xfs reported zoned=1 and that the mountpath directory has the rtinherit flag (t):

    $ xfs_io -c lsattr /data/disk1
    -------t--------X /data/disk1
